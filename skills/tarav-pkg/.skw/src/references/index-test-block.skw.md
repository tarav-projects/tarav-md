# Index.Test.Block.Workflow.Module

> $kw: --from Stable.Surface

Use a `Test.Block` when Index implementation work needs one real, disposable subject that can travel through production mechanics without damaging maintained knowledge.

A `Test.Block` is an ordinary Index block used temporarily as a probe. It is not a surface type, manifest action, parser exception, or second capture model. Its value is precisely that every subsystem must treat it like normal content.

## Contract

- Author the block on a normal discovered Index surface, using the same editor and parser-backed structure as any neighboring block.
- Give it a distinctive ordinary block identity such as `Capture.Test` or `Capture.Test.<tag>` when independent probes must coexist.
- Put only the minimum typed lines needed to exercise the behavior under test.
- Use the real production command or importable service at every boundary being tested. Inject fixtures only at external authority or storage boundaries needed to keep the run isolated.
- Delete the block when the probe is complete. `Stable.Surface` means maintained valuable state, not undeletable state.

The subject identity comes from the block and surface, never its line number. Editing nearby material must not change what the probe names.

## Capture Test Procedure

1. **Isolate durable state.** Prefer a temporary project plus temporary Index, Anchory, and Chat.Index depots so cleanup can remove the whole probe without leaving misleading records. When a live project is necessary, inventory every effect before writing.
2. **Author normally.** Create the ordinary heading and its unanchored typed lines through the same file-writing path used for product content. Do not seed parser objects or stores directly.
3. **Describe one normal landing.** Author one `tarav.index.capture-manifest.v1` document with ordinary target surface and block addresses, exact line bodies, structured message references, content checks, and any real gates.
4. **Preview.** Run `tarav index capture preview --project <root> --manifest <capture.json>`. Require the expected complete effect totals and no stable write.
5. **Land.** Run the corresponding `land` command or the same importable production coordinator. Verify the source attachment, Anchory dossier, `LineRecord`, review and landing gates when supplied, Chat.Index projection, and final audit.
6. **Retry.** Re-run the identical landing and require reuse rather than duplicate anchors, lines, records, or Chat.Index receipts.
7. **Exercise the consumer.** Run the specific linter selector, resolver, gate check, or other Index behavior the probe was created to test. A green capture audit does not substitute for the consumer assertion.
8. **Clean.** Remove the ordinary block and all isolated state. If the run used live shared depots, use explicit normal deletion/reconciliation mechanics and verify that no dangling effect remains; do not merely hide it from discovery.

## Index Implementation Uses

- parser and surface-discovery changes: place the same probe on each affected host kind and require the shared model to resolve it;
- capture changes: assert preview, landing, final audit, bounded reporting, and retry idempotence over the block;
- review or landing-gate changes: use a real tokenized proposal and approval, then inspect the resulting record links and linter verdict;
- linter development: put the `POI.Test` marker inside a `Test.Block` when the test needs a summonable finding as well as an ordinary surface subject;
- cleanup development: start from a successfully landed block, then prove the cleanup leaves no source, record, dossier, or projection that claims the probe remains live.

## Boundaries

- A helper CLI may make cleanup safer, but it must compose normal deletion and reconciliation operations. It must never create a privileged Test.Block landing path.
- Do not add a `test` action to the capture manifest, a test-only parser branch, or direct depot writes that production never performs.
- Do not retain a probe merely because its hosting surface is stable. Preserve only reusable test code and the assertions it protects.
- Do not call a unit test end to end merely because it names every layer. The test is end to end only across the production boundaries it actually traverses.
