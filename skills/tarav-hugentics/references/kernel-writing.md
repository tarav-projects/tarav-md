# Kernel Writing for Notebook capture

Write Lines as focused contributions within an explicitly chosen Block and its
ancestor context. Blocks can organize principles, events, questions, arguments
or other material. They do not need a topic/name field or a concept-only role.
This guide teaches writing craft; selected Types separately govern evidence,
review and checks.

## Writing principles

- **One contribution per Line.** Choose a useful semantic unit. Split a bullet
  that welds unrelated facts or decisions into a paragraph.
- **Distinct sibling contributions.** Aim for orthogonality at the current
  resolution. Remove redundant reformulations; keep a distinction when it
  changes understanding, obligations or future judgment.
- **Direct wording.** State the point plainly. Remove filler while preserving
  qualifications, uncertainty and the User's deliberate distinctions.
- **Use the declared context.** Let the Block and ancestors carry shared
  framing; each Line can concentrate on its semantic delta. Ensure the intended
  reading is recoverable there without silently importing a different Project
  or an arbitrary graph neighborhood.
- **Coverage over compression.** Keep the fundamental angles. An additional
  Line is better than losing a necessary boundary, condition or tradeoff.
- **Useful signal.** Prefer material that can change later understanding or
  judgment. Avoid filler that merely announces a topic already clear in context.
- **Preserve evidentiary meaning.** Keep proposals, examples, decisions,
  disagreements and open questions distinguishable. A discussion does not
  automatically establish a commitment. Preserve User wording when its nuance
  matters; support and exact wording approval remain separate claims.

These are aims, not a universal decomposition algorithm. A Line can be refined
later. Meaning can depend on the Block's other Lines; order matters for logs,
sequences and arguments. Use child Blocks when a more specific context helps.
Children do not retroactively supply required context for their parents' Lines.
No fixed line count, heading syntax, mandatory sections, universal definition
line or compulsory boundary statement follows from this guide.


## Worked examples

In a Block about reviewed capture, this bullet combines several contributions:

```text
- Approval accepts the wording and waits for landing, which writes it, and
  changing the wording invalidates the old approval.
```

A clearer decomposition is:

```text
- Approval accepts the presented wording.
- Landing writes the approved change.
- Changing the wording requires a fresh approval token.
```

Each Line contributes a separate rule. The Block supplies what approval and
landing refer to; repeating the full workflow name on every Line adds little.

Preserve a meaningful qualification:

```text
Weak: Every discussion becomes the current design.
Better: Discussed alternatives become current design only when adopted.
```

In a log Block, order may be part of the meaning:

```text
- The first capture attempt found no source Turn.
- The session refresh exposed the original User Turn.
```

These Lines need not be freely reorderable. Their quality comes from focused
events and intelligible local context. Examples and principles are subject to
the target's actual support requirements; an illustrative example in this
guide is not evidence for a live Project claim.

## Before presenting a proposal

Check the actual target Block and ancestry. For each proposed Line, ask:

1. What distinct information does this add or amend?
2. Is its intended reading recoverable within this context?
3. Can wording be shortened without losing a meaningful qualification?
4. Does it duplicate a sibling Line or belong in an existing Block?
5. Does its support justify the claim's actual strength and status?

Then read the proposed Block as a whole: are important dimensions missing,
contradictions hidden, or unresolved alternatives being presented as settled?
Revise the draft before requesting review, while keeping capture recoverable
when structure or evidence remains incomplete. Do not invent content to fill
a checklist category.
