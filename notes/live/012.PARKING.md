## Index.Block.Approval.Check

- [DF] `Index.Block.Approval.Check` is an `Index.Linter` check that verifies every block changed by an index edit has its own `User.Stamp::Approval` in the supplied Chatlas session ^c20260725-28u
- [DF] `User.Stamp::Approval` is the user-authored event `::approve <Block.Name>` accepting one exact candidate change for that block ^c20260725-28u
- [CT] candidate changes are reviewed one block at a time, even when several approved blocks will be landed together ^c20260725-28u
- [CT] every changed block requires a distinct matching approval event; cluster-level approval does not satisfy the check ^c20260725-28u
- [CT] the changed block’s approval anchor must resolve to its matching user event ^c20260725-28u
- [CT] changing the candidate after approval invalidates its stamp and requires a new approval event ^c20260725-28u
- [DC] the linter receives the current Chatlas session identity and evaluates the edit’s changed-block set ^c20260725-28u
- [DC] a missing, stale, mismatched, or non-user approval raises a POI identifying the affected block ^c20260725-28u
- [PR] the check makes block-level review authority mechanically auditable after every index edit ^c20260725-28u

## Edition.Approval.Token

- [DF] `Edition.Approval.Token` is a proposed formalization where the agent presents a touched index edition proposal together with a short approval token, and approval means the user echoes that token verbatim ^c20260725-45u
- [PR] guiding principle: the agent is responsible for emitting an auditable proposal so the `Index.Linter` can stay simple — complexity lives with the capable producer, not the deterministic checker ^c20260725-45u
- [CT] two independent gates, both required: the user reviews and approves the index line — making it `Reviewed.Content`, an act of accountability, not a correctness verdict — while the linter checks the approval flow is well-formed and auditable; neither substitutes for the other ^c20260725-45u
- [CT] mechanics: the linter parses the proposal on the agent turn and the echoed token on the user turn as a bound pair, making the proposal↔approval binding machine-checkable ^c20260725-45u
- [CT] it captures provenance of the approval act — complementary to `Anchory.Anchor`, which grounds content, not the fact that the user approved this exact edition ^c20260725-45u
- [CT] user cost stays low: approval is a copy-paste of the token, matching the resolved copy-pasteable `User.Command` rendering already landed ^c20260725-45u
- [FR] open: whether the token is a content hash (self-invalidating on any wording edit, forcing re-approval) or an opaque id paired with a separate wording check ^c20260725-45u
- relates to `Index.Block.Approval.Check` above — that note pins `::approve <Block.Name>` as the `User.Stamp::Approval` and the linter check; this note is the token/hash refinement plus the agent-aids-linter and two-gate framing; reconcile the two in a design session ^c20260725-45u
- [DC] the approval token is an opaque nonce linking the user's approval turn to the proposing assistant turn, not a content hash — integrity comes from locating the proposal by its token and comparing the proposal's parsable content to the file ^c20260726-0u
