# The.Agentos.Index

Unified design note for the Agentos Index: a `Soft.Programming.Language` for project knowledge — the `Alignment.Surface` between humans and agents.

ALL CONCEPTS IN THIS NOTE CAN BE REVISED.

Status: **closed — promoted into `skills/agentos-index/` Skill.Package and `001-ontology.md`**

---

## What The Agentos Index Is

The Agentos Index is a `Soft.Programming.Language` for project knowledge.

It is not documentation, not a wiki, not a knowledge base. It is closer to a **program for cognitive operations** that humans and agents run against when they need to reason about the project.

The index is:

- **like code**: a surface to develop, maintain, refactor, and execute
- **a language**: it has syntax (`Dotted.Notation`), semantics (`Index.Block`), a symbol table (`Ontology.Registry`), runtime behavior (`Index.Call`), and an eval loop (`Index.Eval.Loop`)
- **alive**: at any time there is a "current" index — there is no such thing as a "finished" index

The index contains the `Named.Concepts` that are fundamental to the project — the ideas without which something important is missing.

****

## Alignment.Surface

The index is the fundamental `Alignment.Surface` between humans and agents.

It exists precisely at the interface — the shared ground where human and agent align on what things mean. This is its primary purpose: not storage, but **shared grounding**.

Design consequences:

- **readable by humans**: natural language, browsable, self-locating
- **operable by agents**: structured, loadable, searchable, parseable
- **neither side owns it alone**: both contribute, both consume
- the equilibrium is **structured natural language with consistent shape**

A block that's too unstructured for an agent to parse reliably is also too vague for a human to reason from precisely. A block that's too machine-formatted for a human is also too rigid for an agent to use in natural conversation. The sweet spot serves both.

****

## User.Gated.Index

Agents treat the index as **read-only by default**.

The index is the design authority — corrupting it corrupts everything downstream. Agent writes to the index are high-consequence because they change what future agents and humans will reason from.

### Two gates

- `Write.Trigger.Gated` — the user must explicitly initiate write flows; the agent never starts writing on its own
- `Content.Verbatim.Gated` — the user must approve the exact wording of each block before it's committed

### Rules

- agents can **read** freely — the index is their primary grounding source
- agents can **propose** — suggest new concepts, flag gaps, draft blocks
- agents cannot **trigger writes** without explicit user initiation
- agents cannot **commit content** without user approval of exact wording
- the user is the quality gate for what earns a place in the index

This is fundamentally different from `Live.Notes`, where agents may write more freely. The index has a higher write bar precisely because it is the `Alignment.Surface`.

The write loop (in `agentos-index-writer`) is not just a gating mechanism — it is an alignment conversation where human and agent iterate on the precise meaning of a concept together.

****

## Soft.Programming.Language

The index is a `Soft.Programming.Language`: "soft" because the syntax is natural language; "programming" because it has execution semantics.

The code-to-index mapping:

- **Variable declaration** → naming a concept with `Dotted.Notation`
- **Function call** → `Index.Call` — triggered by a `Dotted.Name` or agent reasoning
- **Symbol table** → `001-ontology.md` — the registry of known names
- **Module** → `Index.Note` — a cluster of related definitions
- **Function body** → `Index.Block` — the loadable unit of meaning
- **Type system** → `Index.Block.Syntax` — the structural conventions for writing blocks
- **Import** → loading blocks into agent context
- **Name resolution** → `Index.Name.Resolution` — fuzzy match to canonical name
- **Undefined variable** → `Unresolved.Index.Name` — parked for later
- **Eval loop** → `Index.Eval.Loop` — the sequential pipeline from trigger to grounding
- **Compilation** → maintenance passes — linting, deduplication, structure enforcement
- **Compiler CLI** → `agentos index` — the deterministic tooling surface
- **Runtime** → the conversation itself — where `Index.Calls` execute

The structure comes from conventions (Dotted.Names, block shape, separators), not from rigid formal grammar.

****

## Index.Activation

`Index.Activation` is the mechanism that turns on `Index.Runtime.Semantics` for a session.

- the index runtime is opt-in — it does not magically activate in every conversation
- activation is handled by `agentos-index-activate` — a dedicated bootstrap skill

### Activation chain

```
AGENTS.md: "Load the agentos-index-activate skill at the start of a session."
    → agentos-index-activate loads
    → bootstrap: reads 000-index.md + 001-ontology.md (minimal context)
    → activates Index.Eval.Loop behavior for the session
    → loads agentos-index-trigger for ongoing detection
```

### Activation paths

- **automatic**: AGENTS.md prompts skill load → agent activates on session start
- **manual**: user explicitly invokes `agentos-index-activate` at any point
- **recovery**: if auto-activation fails, the user can trigger it manually

### Manual fallback principle

All index skills must be user-callable as a fallback when the agent fails to trigger automatically:

- agent fails to detect a Dotted.Name → user invokes `agentos-index-resolution`
- agent doesn't suggest registration → user invokes `agentos-index-writer`
- agent didn't bootstrap → user invokes `agentos-index-activate`

The agent automation is the happy path. Manual invocation is the safety net. Same skill, same behavior, different trigger.

Once activated, the agent operates with `Index.Eval.Loop` semantics: Dotted.Names become triggers, concepts are resolved, gaps are detected.

****

## Index.Runtime.Semantics

The index has execution behavior, not just storage behavior.

When an index is active, it is **executed** in real time — concepts are loaded, resolved, grounded, and gaps are detected as the conversation unfolds.

The runtime is **lazy**: concepts are loaded on demand, not preloaded. The agent judges context to decide what needs full loading vs. acknowledgment vs. parking.

Runtime behavior is defined by:

- `Index.Call` — the execution primitive
- `Index.Eval.Loop` — the sequential evaluation pipeline
- `Index.Call.Trigger` — the mechanisms that initiate calls

****

## Index.Call

`Index.Call` is the execution primitive of the index.

An `Index.Call` is initiated by a trigger, then processed through the `Index.Eval.Loop`. The agent evaluates context to decide dispatch intensity:

- concept is central to current discussion → full eval (load blocks, ground)
- referenced in passing → lightweight check (confirm existence)
- unknown but peripheral → park as `Unresolved.Index.Name`
- unknown and central → flag, suggest capture

****

## Index.Call.Trigger

`Index.Call.Trigger` is the mechanism that initiates an `Index.Call`. Multiple trigger types feed into the same `Index.Eval.Loop`.

### Dotted.Name.Trigger

The primary, natural trigger. When a human uses `Dotted.Notation` in conversation, it is a **signal** — not decoration, not casual formatting. It means: "I am referring to a concept that should be grounded."

`Dotted.Notation` is the main **API** of the index — the natural-language interface through which the index is called during conversation.

### Agent.Reasoning.Trigger

The agent proactively fires `Index.Calls` during its own reasoning when it encounters a concept it needs grounding on. The agent is a first-class caller of the index, not just a reactive processor of user signals.

Examples:

- agent is planning implementation and needs to check the design constraints for a concept
- agent encounters an unfamiliar Dotted.Name in a file it's reading
- agent wants to verify its understanding before proposing something to the user

### Explicit.Query.Trigger

Direct invocation via skill or CLI. Examples:

- `agentos index find --query "..."` — deterministic lookup
- a skill explicitly loads index blocks as part of its workflow
- user asks the agent to "check the index for X"

****

## Index.Eval.Loop

`Index.Eval.Loop` is the sequential evaluation pipeline that processes an `Index.Call`.

It is well-defined and consistent — every trigger follows the same pipeline:

```
Trigger → Index.Call → Index.Eval.Loop:

1. Index.Name.Resolution
   - try to match the name against the ontology registry
   - exact match → proceed to step 2
   - approximate match → confirm with human, then proceed
   - no match → proceed to step 3

2. Retrieval + Grounding (resolved path)
   - load relevant Index.Blocks into agent context
   - inject the concept definition so both parties reason from the same base
   - conversation is now grounded on this concept

3. Gap.Detection (unresolved path)
   - is this clearly a new concept? → Emergence.Signal
   - is it approximate to an existing concept? → re-attempt resolution
   - is it peripheral to current discussion? → park as Unresolved.Index.Name

4. Suggestion (when Emergence.Signal)
   - agent holds the concept in working memory
   - may propose capture to user (respecting User.Gated.Index)
   - if user confirms → enters Ontology.Workflows (Registration or Promotion)

5. Parking (when peripheral/unresolved)
   - store as Unresolved.Index.Name in session working list
   - available for later resolution if more context emerges
   - may surface if it keeps recurring
```

The loop ensures consistency: no matter the trigger type, concepts are resolved through the same pipeline.

### Loading behavior

- **default**: load block fundamentals only (~600 chars) — minimal context cost, enough for grounding
- **agent escalates by judgment**: may load full block, related blocks, or even full note if the concept is central to the current task
- **related concepts**: don't auto-load the whole graph — follow links only when judgment says it's needed
- consistent with lazy evaluation: load on demand, escalate on judgment
- no rigid rule — always context-appropriate

### Grounding manifestation

- grounding is reported as a **lightweight footer** at the end of the agent's response
- format: `> Index: loaded `Concept.A`, `Concept.B` | unresolved: `Unknown.Name``
- the agent responds naturally first, then reports index operations at the end
- this gives transparency without interrupting conversation flow
- the user can glance at it, ignore it, or act on unresolved names

### Gap detection aggressiveness (MVP)

- **passive by default**: unresolved names are parked and shown in the footer
- the agent only suggests registration when:
  - the same unresolved name appears 3+ times in the session
  - or the user explicitly asks about it
- this avoids interrupting flow with premature registration prompts
- the footer provides natural visibility — user can choose to act

## Index.Name.Resolution

`Index.Name.Resolution` is a subsystem and skill for resolving names against the index.

- it is difficult for users to reproduce exact canonical names every time
- the agent should be capable of finding the canonical match to reduce duplicated definitions
- this reduces concept drift and duplication — one of the index's main integrity threats

### Index.Name.Resolution.Skill

- `Index.Name.Resolution` is implemented as its own skill (`agentos-index-resolution`)
- a skill gives space to develop complex behavior over time
- the skill is the abstraction boundary — internals can evolve without changing the interface

### MVP behavior (fully agentic)

- reads `000-index.md` and `001-ontology.md` as entry points
- follows its instincts from there — scans blocks, reads notes as needed
- uses the **whole block** for matching, not just the `findability:` field
- uses the **whole chat context** for discovery — the Dotted.Name is the trigger, but resolution uses surrounding conversation and common sense
- `findability:` is a performance hint — extra info to help search, not the only input
- returns: resolved canonical name OR unresolved

### Future evolution

- may call CLI (`agentos index find ...`) for deterministic search
- may use embedding-based semantic similarity
- may use external search engines
- all strategies are on the table — the skill boundary protects the interface

### Resolution behavior

- when a name doesn't exactly match the registry → search for close equivalents
- matching is semantic (meaning-based), not just string similarity
- if a likely match exists → ground the conversation using the canonical name
- if no match → treat as a potential new concept (feeds into Gap.Detection)

****

## Unresolved.Index.Name

`Unresolved.Index.Name` is the result when an `Index.Call` cannot resolve a name and the concept is not clearly new.

The agent parks it in a session working list. It remains available for:

- later resolution if more context emerges
- suggestion to the user if it keeps recurring
- explicit registration if the user confirms it's a new concept

This is the "undefined variable" of the index — acknowledged but not yet resolved.

****

## Bullet.Point.Sentence

`Bullet.Point.Sentence` is the writing style for the entire index.

- bullet-pointed sentences, one idea per line
- indentation for qualification or sub-points
- blank lines to separate bullet paragraphs (logical groups)
- this is how the user writes naturally — the index adopts this style as THE style

Writing guidelines (paper-abstract style):

- each bullet is one self-contained statement
- together they give the minimal mental model needed to reason correctly
- locating (what kind of thing is this) — use common sense, no rigid categories
- differentiating — only when genuinely valuable, don't force it
- not explanations, not filler — just fundamentals
- concise, direct, high-signal per line

****

## Index.Block

`Index.Block` is the fundamental semantic unit of the index — the loadable unit of meaning.

- the smallest node in the index knowledge graph
- the unit loaded into agent context during `Index.Eval.Loop`
- anchored by a heading (H2–H6) that names the concept using `Dotted.Notation`
- like a class in Python: identity, properties, behavior, constraints

### Properties

A block must be:

- **loadable**: small enough to fit in agent context without waste (25-line ceiling = context-budget constraint)
- **grounding**: gives the agent enough to reason correctly about the concept
- **precise**: reduces ambiguity between what the human means and what the agent understands
- **coupled-but-addressable**: lives in its proper note but can be pulled into context independently

### Block layers

1. **Heading** — identity (the `Dotted.Name`)
2. **Fundamentals** (= the body) — bullet-point sentences, the concept's essential content
3. **Extra** (optional) — examples, code, clarifying material when fundamentals alone aren't enough
4. **Index section** (optional) — findability, related, operational meta

- fundamentals aren't a special section — they're just what the block IS
- the block is fundamentals by default — the whole body is bullet-point sentences
- extra material is additive — examples, diagrams, code appear below for clarity
- blank lines separate bullet paragraphs — each group is a logical unit
- the 25-line ceiling forces compression — if you can't fit it, split the block

****

## Index.Block.Syntax

`Index.Block.Syntax` is the structural convention for writing `Index.Blocks` — the "type system" of the index.

- separates *how a block is written* (syntax) from *what it means* (semantics)
- the concrete target for linting rules and block shape validation

### Universal block shape

```markdown
## Dotted.Name

- [fundamental statement]
- [fundamental statement]
    - [qualification or sub-point]
- [fundamental statement]

- [another bullet paragraph — different facet]
- [statement]
    - [sub-point]

[optional: examples, code, etc. — only when fundamentals alone aren't enough]

### index

- findability: [aliases, keywords, approximate names]
- related: `Related.Concept.One`, `Related.Concept.Two`
```

### Fields

| Field | Required? | Purpose |
|---|---|---|
| **Heading** (H2–H6) | required | identity — names the concept |
| **Fundamentals** | required | grounding — bullet-point sentences, the essential content (~600 chars) |
| **Extra** | optional | depth — examples, code, clarifying material |
| **Index section** | optional | meta — findability, related, operational |

### Size constraint

- **line limit**: 25 lines per block (hard ceiling)
- **character limit per line**: enforced to keep lines focused (not wall-of-text bullets)
- both are context-budget constraints, not aesthetics
- if too big: carrying more than one idea → split into sibling blocks
- or idea is complex → split into chunks under sub-headings within the note

### Write first, polish later

- the linter does NOT run at write time — writing is frictionless
- `agentos-index-writer` focuses on meaning alignment (`Content.Verbatim.Gated`), not format enforcement
- linting happens later: during maintenance passes, doctor reviews, compilation
- getting concepts into the index matters more than perfect format
- format issues are caught and fixed as maintenance work

### Opening sentence

- free natural text — no rigid format enforced
- the first fundamental bullet(s) set the tone for the block
- linter checks existence and length, not format

### Separator requirement

- `****` separators between H2-level blocks are **mandatory** in index notes
- this makes all index content machine-parseable by the `mdblocks` toolchain
- enforced by `agentos index doctor` (CLI) and `agentos-index-doctor` (skill)
- existing notes without separators should be migrated as a maintenance task

### Linting

`Index.Block.Syntax` is enforceable by tooling:

- currently: `agentos mdblocks lint` (block-level)
- future: `agentos index lint` (index-level, including semantic checks)

The linter is the "compiler" — it catches structural violations before they become reasoning errors.

****

## Index.Note

`Index.Note` is the module-level container — a cluster of related `Index.Blocks`.

An index note is centered on one named concept or a tight concept cluster. It is both an organizational unit AND a semantic unit.

### Notes carry meaning

- the first header + opening paragraph define what the note IS (its semantic identity)
- this note-level semantics affects how its blocks are interpreted
- blocks are the main semantic units, but they are coupled to their note context
- blocks should be useful independently but not arbitrarily portable

### Mechanical roles

Notes implement hierarchical discoverability:

- file organization = navigation structure
- some notes have special mechanical meaning (reserved notes: `000-index.md`, `001-ontology.md`)
- the numbering system provides stable handles

### Properties

- one concept or tight cluster per note
- numbered with a stable 3-digit prefix
- the filename is the stable handle; the title may evolve
- the note header establishes context for all blocks within

****

## Dotted.Notation

`Dotted.Notation` is the language of the index — the syntax for naming concepts.

A dotted name is a **signal** that the phrase refers to a concept, not casual prose. It is also the primary **trigger** for `Index.Call` execution via `Dotted.Name.Trigger`.

### Rules

- every ontology name has at least two parts
- dot depth is flexible and natural to the concept
- dots provide context but are not a strict hierarchy
- definitions and relationships live in blocks, not in the name alone
- `Ontology.Namespace` must be explicit; do not infer from prefix

### Dotted.Parameterized.Notation

`<Concept>.Name::Target` identifies an instance of a named concept without creating a new concept.

- the part before the sigil is the concept
- the part after the sigil is the parameter (the target)
- parameterized references are instances, not different concepts
- use a new dotted name when the meaning changes
- use a `::` type statement when the same concept is applied to a different target

Examples: `Maintenance.System::Agentos`, `Md.Surface::Agentos.Stack`

### Variable.Notation

`<Variable>.Name` expresses a family of names — an open/variable part.

- angle brackets mark the variable part
- it means "any name of this form" — not one specific concept
- example: `<Concept>.Name:<Target>` — both parts are open
- distinct from parameterized notation which has a specific concept and a specific target

### Dotted.Name.Detection

Detection rules for recognizing a `Dotted.Name` in conversation (used by `agentos-index-trigger`).

All shapes share the same signal: **capitalized words joined by dots, always two+ parts**.

Shapes and patterns:

```
Basic:            Word.Word(.Word)*
                  e.g. Index.Block, Soft.Programming.Language

Parameterized:    Word.Word(.Word)*:target
                  e.g. Maintenance.System::Agentos, Md.Surface::Agentos.Stack

Variable:         <Word>.Word(.Word)*
                  e.g. <Concept>.Name, <Target>.System

Variable+Param:   <Word>.Word(.Word)*:<target>
                  e.g. <Concept>.Name:<Target>
```

Regex-like definitions:

```
Basic:          [A-Z][a-z]+(\.[A-Z][a-z]+)+
Parameterized:  [A-Z][a-z]+(\.[A-Z][a-z]+)+:[A-Za-z][\w\-\.]*
Variable:       <[A-Z][a-z]+>(\.[A-Z][a-z]+)+
Variable+Param: <[A-Z][a-z]+>(\.[A-Z][a-z]+)+(:<[A-Z][a-z]+>|:[A-Za-z][\w\-\.]*)
```

NOT triggers (exclusions):

- abbreviations: `e.g.`, `i.e.`, `etc.`
- filenames: `file.txt`, `config.json`, `SKILL.md`
- URLs: `github.com`, `anthropic.com`
- lowercase dotted: `user.name`, `object.method`
- single-part names: just `Index` alone is not a trigger

## Ontology.Registry

`001-ontology.md` is the **symbol table** of the index.

It is the official entry point to the ontology — the registry of all named concepts and the primary lookup surface for `Index.Name.Resolution`.

### Two navigation trees

The index has two parallel navigation structures:

- `000-index.md` — entry point to the **file organization** (which notes exist, where to start reading)
- `001-ontology.md` — entry point to the **ontological organization** (which concepts exist, how they relate)

These are complementary views of the same knowledge graph.

### Role

- low-resolution concept inventory
- compact definitions (1–3 sentences per concept)
- pointers to fuller notes when they exist
- the lookup surface for `Index.Name.Resolution`
- organized into `Ontology.Namespaces` — explicit groupings that can multiply freely

### The knowledge graph view

The index is ultimately a knowledge graph:

- blocks are the smallest nodes
- notes are clusters of related nodes
- the ontology registry is the entry point to the graph
- all content should evolve to be under a named concept

****

## Ontology.Namespace

`Ontology.Namespace` is an explicit bounded organizing view over ontology concepts.

Namespaces:

- are not inferred from dotted notation
- are not exclusive ownership containers
- may overlap — a concept can appear in multiple namespaces
- must be explicitly declared
- can multiply freely from `001-ontology.md` as the entry point

### Ontology.Integration.Hook

A namespace where one project records external concepts it consumes from another project's ontology, plus local interpretation, implementation mode, constraints, or mappings.

****

## Ontology.Workflows

Concepts have a natural lifecycle in the index. These workflows are well-defined so agents can participate in index maintenance through the `Index.Eval.Loop`.

### Emergence

- a concept appears informally in discussion or prose
- someone uses `Dotted.Notation`, firing a `Dotted.Name.Trigger`
- the `Index.Eval.Loop` detects it as unresolved → `Gap.Detection` → `Emergence.Signal`
- the concept lives in the agent's working memory initially

### Registration

- when the concept stabilizes, it gets a compact entry in `001-ontology.md`
- triggered when concept identity matters: design discussions, naming decisions, repeated `Unresolved.Index.Names`
- the user gates registration (agent proposes, user approves — `User.Gated.Index`)

### Promotion

- when a concept has enough weight, it gets a dedicated `Index.Note` with full `Index.Blocks`
- a concept can have a registry entry without a note
- a concept can have a note without going through registry-first

### Rename and cleanup

- concept names may evolve, but dotted names in published surfaces should be updated together
- stale or duplicate names are caught during maintenance passes or by `Index.Name.Resolution`
- the ontology registry is the lookup surface for current canonical names

## SSOT Rule (revised)

The index is the **definitional authority** for all named concepts in the project.

Like the index of a book: it tells you what exists and what it means. The chapters (other surfaces) contain the full treatment. You don't read the whole book to understand what a term means — you look it up in the index.

### The non-negotiable

- every `Dotted.Name` is defined in the index and nowhere else
- the index is the SSOT for conceptual definitions
- for anything sufficiently relevant in the project → name it → write a block in the index

### What the index contains per concept

- what it IS (the definition)
- why it exists (rationale)
- how it connects to other concepts (relationships, integration)
- user preferences and gated decisions
- boundaries (what it is NOT)

### What lives on other surfaces (the further detail)

A concept's full treatment may span multiple surfaces — each holds a different facet:

- **code**: exact implementation — classes, fields, methods, flags
- **CLI help**: usage interface — commands, flags, examples
- **skills**: operational behavior, reusable workflows
- **AGENTS.md**: project-local agent guidance

These are **further detail**, not definitions. The conceptual definition always lives in the index.

### Extraction rule

When something becomes explicit in another surface (especially code):

- the index keeps the conceptual definition (what, why, how it connects)
- the index links out to the surface where the explicit/mechanical detail lives
- do not duplicate what the code or CLI already says precisely
- a block can have a **conceptual declaration** + a **link out** for the full mechanics

### The index as entry point

- by traveling the index, an agent should reach all `Stable.Surfaces` of the project
- the index is the main entry point for understanding the whole system
- it achieves this through definitions and links — not by containing all detail

****

## Stable.Surface

A `Stable.Surface` is a durable, authoritative surface where a specific facet of project knowledge lives.

- each `Stable.Surface` is the best place for its kind of information
- a project has multiple `Stable.Surfaces` — the index is one of them
- the index links to all other `Stable.Surfaces`, making the full system navigable

### Examples

- **Index** (`notes/index/`) — conceptual model, ontology, rationale, preferences
- **Skills** (`skills/`) — public reusable behaviors, operational specs
- **CLI help** — command interface, flags, usage
- **Codebase** — current implementation (the full mechanical description by construction)
- **AGENTS.md** — project-local agent workflow guidance

### Relationship to the index

- the index references all `Stable.Surfaces` but does not contain them
- the index provides enough grounding to navigate to where the full definition lives
- the index is the conceptual layer above the other surfaces

****

## What Belongs In The Index

The index contains `Named.Concepts` — ideas that are fundamental to the project.

### The test

A concept belongs in the index when:

- it is long-lasting (survives across sessions, agents, and time)
- it is fundamental (without it, something important is missing)
- it changes future judgment (knowing it affects how decisions are made)
- it can be named (forced into `Dotted.Notation` with a precise definition)

### What does NOT belong

- transcripts, changelogs, session-specific state
- implementation dumps (code belongs in code)
- progress dashboards, task lists (these live in live notes)
- generic tutorials
- anything that doesn't survive the "name it precisely" test

****

## Low-Friction Capture

The path from idea to storage must have zero friction.

This is an operative concern — the index evolves just as code does. At any time there is a "current" index; there is no finished state.

Rules:

- the user must never spend time thinking about where a note should go
- useful material can enter before it has mature structure
- rough notes, partial concepts, stubs are acceptable when the knowledge is important
- organization and polish are maintenance steps, not prerequisites
- the `Stub.Convention` defines the minimum viable index entry

****

## Stub.Convention

Incomplete index entries are allowed when they still contain minimal durable signal.

A valid stub must have:

- a real concept boundary (a `Dotted.Name`, not just a placeholder)
- a short definition or description (at least one grounding sentence)
- explicit acknowledgment of incompleteness
- useful direction for future work

A stub that is just a title with no content is not a valid index entry. But a stub with a name and one precise sentence IS valid — it registers the concept's existence and boundary.

****

## Promotion Model

Knowledge flows toward the index through promotion.

Material starts wherever it naturally appears: chat, live notes, skills, AGENTS.md, code comments, design sessions. When it becomes durable design truth, it should be promoted.

Signs of a promotion candidate:

- referenced repeatedly from outside its current location
- defines a concept that multiple agents or sessions need
- captures a constraint or decision that would be lost if the current surface is discarded
- lives in a skill but is really design truth, not operational guidance
- keeps appearing as `Unresolved.Index.Name` in conversations

Promotion is a maintenance activity, not a gate on initial capture.

****

## Maintenance Model

The index is maintained through constant additive improvement — like code maintenance.

### Philosophy

- the index is never complete
- each pass should leave things slightly better aligned
- small, frequent passes beat large infrequent ones
- maintenance is diagnosis-first, not fix-first

### Maintenance as "compilation"

Maintenance passes are the index equivalent of compilation:

- **linting**: `Index.Block.Syntax` enforcement, size constraints, separator presence
- **deduplication**: merging overlapping concepts (caught by `Index.Name.Resolution`)
- **naming cleanup**: aligning names with the ontology registry
- **registry sync**: adding new concepts, updating stale entries
- **promotion**: pulling durable truth from other surfaces
- **stub resolution**: expanding stubs or removing empty ones
- **index routing**: keeping `000-index.md` and `001-ontology.md` current

### What maintenance is NOT

Maintenance is note-level work, not project progress tracking. It should not turn the index into a changelog, task list, or status dashboard.

****

## Index.Note.Style

`Index.Note.Style` is the desired mature shape for stable index notes.

A mature index note is:

- **concept-centered**: organized around a `Named.Concept`, not a task or timeline
- **block-structured**: meaning is carried in discrete `Index.Blocks`
- **high-signal**: every block and every line earns its place
- **low-prose**: bullets and short declarative statements over essay-style paragraphs
- **self-locating**: the title and opening line ground the reader immediately
- **note-coupled**: blocks belong in their proper note — not arbitrarily portable

This is a convergence target, not a gate. The `Stub.Convention` is the minimum entry bar.

## Index.CLI

`agentos index` is the future CLI surface for deterministic index operations — the "compiler" of the index.

It will own:

- **doctor**: `agentos index doctor` — detect separator issues, syntax violations, index health problems
- **linting**: `Index.Block.Syntax` validation, size enforcement, structural checks
- **lookup**: deterministic concept search and block retrieval
- **name resolution**: supporting `Index.Name.Resolution` programmatically
- **registry sync**: checking ontology registry completeness and staleness
- **compilation reports**: summary of index health

Currently, lower-level block operations exist via `agentos mdblocks`. The `agentos index` surface will build on top of `mdblocks` with index-specific semantics.

### Block Extraction (current)

- `agentos mdblocks blocks` — parse blocks anchored by `****` + H2–H6 headings
- `agentos mdblocks links` — emit companion links for separator-anchored blocks
- `agentos mdblocks lint` — lint blocks; enforces the 25-line hard limit
- `agentos mdblocks find --query ...` — find best-matching blocks by query

The `****` separator is the bridge that makes human-readable index structure machine-parseable.

## File.Numbering.Protocol

Numeric filename prefixes provide stable, addressable handles for index files.

This is a convenience — it does not define anything fundamental about the index semantics. But it supports the mechanical layer:

- 3-digit zero-padded prefix: `NNN-Title.md`
- assigned prefixes are permanent
- gaps are allowed; allocation is append-only
- allocate with `agentos prefix next`
- range: `000-099` reserved, `100-499` index notes, `500-999` other

## Implementation: Skill Architecture

This design is an MVP. The implementation target is a `Skill.Package` (see `notes/index/113-Skill.Package.md`) that operationalizes the index runtime.

`agentos-index` is the `Main.Skill`. Companion skills are `Alias.Skills` — lightweight entry points that point to the relevant `agentos-index/references/` file.

### `agentos-index` (meta skill)

The master skill that contains the full index design and operational semantics.

- **role**: meta skill — defines the index model, eval loop, block syntax, naming rules, and all index concepts
- **structure**: compact SKILL.md + extensive `references/` files for each major concept area
- **loaded by**: other index skills that need the full design context
- **contains**: the design truth for the index system (this live-note content, promoted into skill form)

This is the `Design.Target.Model` of the index expressed as a skill — the authoritative reference that other skills derive from.

### `agentos-index-activate`

The bootstrap skill that activates the index runtime for a session.

- **role**: one-time session initialization — read minimal index files, establish context, activate runtime
- **behavior**:
  - reads `000-index.md` and `001-ontology.md` (minimal bootstrap)
  - may read additional notes relevant to the current task context
  - loads into context the minimal set of concepts/guidance needed for the runtime:
    - how to detect `Dotted.Names` (recognition rules)
    - what the `Index.Eval.Loop` is (condensed)
    - what the footer format looks like
  - activates `Index.Eval.Loop` behavior
  - loads `agentos-index-trigger` for ongoing detection
- **callable by**: AGENTS.md auto-load OR user manual invocation
- **design goal**: reliable bootstrap that always works, whether auto or manual
- **key constraint**: must inject enough inline guidance that the agent can operate the basics without loading more skills immediately

### `agentos-index-trigger`

The lightweight detection skill that makes the `Index.Eval.Loop` fire during normal conversation.

- **role**: prompt the agent to detect `Dotted.Notation` in conversation and initiate `Index.Calls`
- **behavior**:
  - watches for Dotted.Names in user messages
  - triggers `Index.Name.Resolution` against the active index
  - dispatches through the `Index.Eval.Loop`
  - loads `agentos-index` when full context is needed
- **callable by**: `agentos-index-activate` (automatic) OR user manual invocation
- **design goal**: minimal prompt footprint — just enough to activate the runtime behavior
- **future**: should eventually be absorbed into `agentos-index` itself once the trigger behavior is stable

### `agentos-index-writer`

The write-path skill — implements `User.Gated.Index` with two explicit gates.

- **role**: the controlled write interface to the index
- **gates**:
  - `Write.Trigger.Gated` — the user must explicitly initiate the write flow; the agent never starts writing on its own
  - `Content.Verbatim.Gated` — the user must approve the exact wording of each block before it's committed
- **callable by**: user manual invocation only (never auto-triggered by the agent)

### Write loop

The writer operates as an interactive alignment conversation, one block at a time:

```
User triggers write → agentos-index-writer activates

For each block to write/modify:
    1. Show proposed block (diff view for updates, full block for new)
    2. User reads, suggests changes
    3. Agent shows revised version
    4. Repeat until user accepts
    5. Move to next block

All accepted → enforce Index.Block.Syntax → lint → commit to index
```

- each block gets individual attention — no bulk-approve
- the user always sees final form before anything touches the files
- the loop is an alignment opportunity — human and agent refine wording together
- handles: new concept registration, block creation, block updates, ontology registry entries
- enforces `Index.Block.Syntax` on all writes
- runs linting before committing

### `agentos-index-resolution`

The name-resolution skill — implements `Index.Name.Resolution`.

- **role**: resolve approximate or unknown names against the index
- **behavior**:
  - called by the eval loop when a name needs resolution
  - reads `000-index.md` and `001-ontology.md` as entry points
  - uses the whole block content for matching, not just `findability:`
  - uses the whole **chat context** for resolution, not just the Dotted.Name itself
    - the Dotted.Name is the trigger, but discovery uses common sense + surrounding conversation
  - returns: resolved canonical name OR unresolved
- **MVP**: fully agentic — agent judgment, no special tooling
- **future**: may integrate CLI search, embeddings, or external engines

### `agentos-index-doctor`

The index health review skill — diagnosis-first quality checks.

- **role**: agentic review of index quality when the user wants a health check
- **behavior**:
  - can call `agentos index doctor` CLI for deterministic checks
  - adds agent judgment on top: staleness, concept coherence, coverage gaps
  - reports issues with evidence, suggests fixes (does not auto-fix)
- **callable by**: user manual invocation
- **checks**: separator presence, block syntax, ontology staleness, naming issues, unrouted notes

### Skill relationship

```
agentos-index-activate (bootstrap, one-time per session)
    → reads 000 + 001 (minimal context)
    → activates Index.Eval.Loop
    → loads agentos-index-trigger

agentos-index-trigger (lightweight, always-on detection)
    → triggers Index.Eval.Loop
    → calls agentos-index-resolution for name matching
    → loads agentos-index (full context) when needed
    → calls agentos-index-writer when write is needed

agentos-index (meta skill, full design reference)
    → loaded by other skills for design truth
    → contains references/ for each concept area

agentos-index-resolution (name resolution)
    → called during Index.Eval.Loop step 1
    → reads index entry points + block content + chat context
    → returns resolved name or unresolved

agentos-index-writer (write gate)
    → called by user when index modification is needed
    → enforces User.Gated.Index (Write.Trigger.Gated + Content.Verbatim.Gated)
    → enforces Index.Block.Syntax

agentos-index-doctor (health review)
    → called by user for index quality checks
    → uses agentos index doctor CLI + agent judgment
    → reports issues, does not auto-fix
```

### Manual fallback principle

All skills are user-callable. The agent automation is the happy path; manual invocation is the safety net:

- `agentos-index-activate` — user says "activate the index"
- `agentos-index-trigger` — user says "check for index calls"
- `agentos-index-resolution` — user says "resolve `Some.Name`"
- `agentos-index-writer` — user says "write this to the index"

1. **Design phase** (current): converge on this live-note until the concepts are stable

3. **Build `agentos-index`**: promote this design into the meta skill with references
