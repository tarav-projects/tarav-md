## Explicit Type Workflow

The User accepted an explicit `TypeWorkflow`, specifically the ownership
relationship `entity(TaravClass).workflow` pointing to that workflow. The
decision is captured in [the record framework](../record-framework.md#explicit-type-workflow);
this capture does not implement the ownership change.
<!-- tarav.breadcrumb 93e0b6e337c1 -->

The discussion separated foundational code location from semantic ownership:
code can remain in `tarav.kernel` while types belong to specialized workflows.
The User also affirmed that the Type Graph expresses explicit type semantics,
not necessarily all of the system's meaning.

## Behavioral contracts embedded in types

The User proposed embedding tests and their necessary support in the type
hierarchy: a base type can ship a behavioral suite and require subtypes to
comply with it. The User emphasized that these are actual behavioral checks,
not only enforcement that test-support methods exist. The discussion calls
this [Type-bound Conformance Contracts](../record-framework.md#type-bound-conformance-contracts).
<!-- tarav.breadcrumb 6f17ec076005 -->
<!-- tarav.breadcrumb a63ef2db9d82 -->

The User affirmed that the hierarchy carries operational capabilities,
contextual knowledge, and executable behavioral obligations together, with
the Type Graph making that structure discoverable. This capture records the
design direction without implementing its test machinery.
<!-- tarav.breadcrumb f29d080a69d3 -->

## Capture organization and multiple paths

Using Wiki capture as the example, the User affirmed that skills are primary
workflow entrypoints and that workflows commonly combine instructions and
Python mechanics. The preferred implementation route is `Capture → Wiki`,
grouping capture operations together while treating Wiki as their destination
and surface model.
<!-- tarav.breadcrumb b6be2b2522ae -->

The discussion established that `.workflow` and the code hierarchy express
one organization selected for implementation needs, without semantic priority
over other organizations. Other workflows can group the same objects or model
a view without any objects naming them through `.workflow`. Those additional
Diagram paths remain future modeling work. The principle is retained in
[Diagram workflows](../diagram-workflows.md#one-implementation-path-among-several-organizations).
