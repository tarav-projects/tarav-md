## Programs defined by Project classes

The User settled on Programs as ordinary Tarav classes defined in Projects,
using their existing trusted Python environment. The shared base provides
execution and persistence; concrete definitions supply States, Actions and
allowed connections. The User then requested an implementation request and
execution, with Project Monitor changes left for another discussion.

status under its token. This aligns arrival with the promise of maintaining
that State. A token selects which conditions to check; product drift can still
occur and must be reported. The refined design lives in
[Programs](../programs.md#project-defined-checked-programs--2026-10-23).

## Global command routing for Studio execution

The User narrowed the next implementation to a global CLI router. It maps a
chosen Tarav command to an external invocation, forwards its arguments, and
can call SSH directly to run the same command on the Studio. Run profiles,
an SSH subsystem and the Chatlas vector database are separate future work.

implementation evidence; [request 956](../../../../tarav-py/notes/live/956-global-cli-command-router-impl-req.md)

## Programs refined into Action graphs

The User refined the earlier Program model until an explicit State object was
unnecessary. Both occupying a node and performing an edge are Actions, so the
existing publication and registry machinery can represent the work directly.
The Program owns check selection and may reuse Check classes across Actions.
Mandatory engine rules concern current tokens and allowed graph movement,
rather than imposing ownership or fixed meanings for checks.

and [Wiki request 880](../../live/880-program-action-graph-wiki-impl-req.md).

lifecycle checks, multiple active occurrences and external Action visibility.

## A Typesense product integration for Chatlas

The User selected deploying Typesense first, with a thin Tarav adapter carrying
conversation text, available metadata and exact Chatlas references. Tarav code
is developed here and published to GitHub for the Studio to pull; Typesense
itself must not be installed on the control Mac.
<!-- tarav.breadcrumb c11beeb15734 -->

`tarav chatlas typesense` is the agent-facing namespace. Its implementation has
no Studio or SSH knowledge; the existing CLI router supplies that invocation.
Input is limited to existing Normal Model files, without reading raw transcripts
or triggering normalization.

[Chatlas Typesense](../chatlas-typesense.md) retains design and current deployment
standing. The adapter passed 15 initial and 103 broader tests using an HTTP
contract fixture; this is not a live engine/relevance benchmark. Studio
deployment files are prepared for the operator's Ansible run. The Git-only
upload lacks ignored Normal Model files, so their transfer is explicit.
