## The Diagram as Tarav's semantic glue

The discussion reframed The Diagram as the graph that already emerges from
Tarav's Records, registered classes, Types, Ships, References, Entities, and
workflow-defined relationships. It is embedded in Tarav's operation rather
than requiring every participating object to live under a dedicated
`tarav.diagram` package or store. The Record-to-class relationship is itself
one of the first Diagram relationships.
<!-- tarav.breadcrumb 31a6a7ae06ee -->

Tarav Records and native Artifacts remain distinct connected surfaces.
Records are lightweight Tarav-owned JSON statements whose code owns their
interpretation and mechanics. Artifacts may be Markdown, code, repositories,
chat sessions, or other material outside Tarav's control. References may
point anywhere, including back into The Diagram, while meaningful external
subjects can acquire representative Entity Records in it.

## Workflows as named applications

A Workflow is a named bundle of functionality, analogous to an application.
Workflows may overlap, expose Records and relationships, operate directly on
native Artifacts, and populate or consume The Diagram. Their common language
is the kernel's Records, Types, Ships, References, and navigation mechanics;
each Workflow continues to own its particular vocabulary and behavior.
<!-- tarav.breadcrumb e7ecdf7a526b -->

`TaravSpace` names the conceptual Record space exposed through registered
Workflows. It does not prescribe one in-memory object or storage strategy.
Workflows decide how their Records are enumerated and loaded, while a common
filesystem-like interface lets agents progressively list, read, resolve, and
expand context.
<!-- tarav.breadcrumb 8a1c10c37565 -->

## Minimal tarav-py organization

The first useful architectural split is deliberately small: `tarav.kernel`
owns the shared Record, identity, Reference, Type, Workflow, registry, and
space mechanics; `tarav.workflows` contains named applications such as
Context, Archive, Chatlas, Breadcrumbs, Scoring, and SKW; `tarav.runtime`
selects and composes registered Workflows; and CLI and daemon remain consumers
of the Python library. Context is one built-in Workflow, not a separate
architectural layer. The Python library remains Tarav's primary interface for
agent-written queries and mutations.

The design is integrated in the [record framework](../record-framework.md)
and [Context Graph](../context-graph.md) topical notes.

## Tarav as an executable ontology

The true foundational unit is `TaravObject`. Every Tarav object has a Record
representation and Record capabilities, but retaining that Record is optional.
A loaded object may obtain its Record from JSON, while a runtime-only object
may compute it from code and current state. The Record need not contain every
fact about the object: meaning resides in the complete pair of Record and
implementing class.
<!-- tarav.breadcrumb bce69653a2de -->
<!-- tarav.breadcrumb 5bedd719c55d -->

The Diagram is the emergent ontology formed by those objects and their
relationships. A subject participates when Tarav can represent it as a
`TaravObject`. This includes runtime instances, Python classes, Workflows, and
Tarav itself. Code therefore enters the Diagram as an Artifact represented by
Tarav objects rather than as a separate special case.
<!-- tarav.breadcrumb b39d7f6f7b1d -->
<!-- tarav.breadcrumb 4389f5e64eed -->

## Type, object, and entity participation

`TaravType` supplies class-level participation in the Diagram.
`TaravObject(TaravType)` adds instance participation and the default Record
contract, while `TaravEntity(TaravObject)` adds durable identity. All
maintained Tarav classes should normally derive from `TaravType`, including
classes whose instances are navigation views or implementation helpers,
because agents also need to discover and contextualize Tarav's own code.
<!-- tarav.breadcrumb 9cec6e096e79 -->
<!-- tarav.breadcrumb 730233cadd01 -->

A `TaravClass(TaravEntity)` reifies a Python class as an ordinary object in
the Diagram. The Python class and its representative Entity remain distinct;
the class's `TypeShip` connects them. A `TaravWorkflow(TaravEntity)` similarly
represents a Workflow instance, whose Entity Ship is distinct from the
TypeShip identifying its implementation class. A global `TaravSystem` Entity
can represent Tarav itself independently of the Python package that implements
it.
<!-- tarav.breadcrumb 39fd7e28ecbc -->
<!-- tarav.breadcrumb d64fd7a7d6ee -->

## Context becomes core navigation

The later discussion superseded today's earlier placement of Context as one
optional built-in Workflow. `context(subject)` is a core Diagram operation,
analogous to opening a node as a directory. It dispatches to the
`class_context()` hook for a class and the `obj_context()` hook for an
instance, returning a lazy, progressively navigable `Context` view.
<!-- tarav.breadcrumb 4973704a9a0c -->
<!-- tarav.breadcrumb ef3505c7f99d -->
<!-- tarav.breadcrumb 6be04841b415 -->

For now, a `Context` instance is a navigation handle rather than a subject in
the Diagram. Its class still derives from `TaravType`, so agents can inspect
how Context works through the same class-reification mechanism. Record schemas
for Context views remain unnecessary until retaining a particular view becomes
a real use case.

## Python architecture documentation refactor

The User identified that `tarav-py/ARCHITECTURE.md` had grown into a detailed
implementation manual and selected a narrower role: it should explain the
architecture that code alone cannot explain. The document was rebuilt around
Tarav's executable ontology, bootstrap path, package layers, compact domain
ownership, integration invariants, and sources of truth. Detailed class APIs,
schemas, migrations, and subsystem mechanics now defer to code, tests, and the
Project Wiki. The resulting overview is 193 lines instead of 433.
