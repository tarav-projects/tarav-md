## Tarav objects and JSON representation

The discussion distinguishes a Tarav object, its actionable interpretation in
code, from a record, its serialized representation, particularly in storage.
The preferred semantic root is `TaravObject`, replacing the storage-oriented
`TaravRecord` name. A separate record subclass is not needed merely to express
serialization; loading is one behavior of the semantic object.
<!-- tarav.breadcrumb 699bd233390b -->

Shared mechanics can include `help()`, a type label, and a Type Ship UUID,
independently of file, directory, or inline placement. An actionable `SkwBlock`
can therefore remain serialized inside its containing document.
<!-- tarav.breadcrumb d828b5170ed5 -->

Writing to storage remains the responsibility of the class or producing
workflow. Tarav formalizes reading into the declared registered class; each
class owns producing a representation that it can interpret.
<!-- tarav.breadcrumb 84003feaf351 -->

The proposed common in-memory representation contract adds `to_json()` and a
static `json_example()`. The example serves both agent documentation and a
minimum default round-trip test for registered classes. It represents the
object, not necessarily whether or how it is stored.
<!-- tarav.breadcrumb 78cc939079aa -->

Add `from_json(value)` alongside the existing `json_load(file)`: construction
from an in-memory representation and loading a JSON stream remain distinct
entry points.
<!-- tarav.breadcrumb 577e239a8a8d -->

The minimum default test follows example JSON → object → JSON → object → JSON,
checking successful conversion and retained information. This is the default
baseline test for the contract.
<!-- tarav.breadcrumb 6881ce585fe7 -->
<!-- tarav.breadcrumb 49148b20a481 -->

This captures the design discussion; it does not report implementation of the
proposed object contract. See [the topical note](../record-framework.md#tarav-objects-and-json-representation).

## RecordInterface as a basic object contract

The discussion extended the object design with an explicit record interface
for structural data requirements. Data is first-class alongside behavior, and
`TaravObject` itself must provide `RecordInterface`. Pydantic was selected as
the supporting machinery, and implementation was requested.
<!-- tarav.breadcrumb 35cf58038df8 -->
<!-- tarav.breadcrumb 80b2fc57c9d5 -->
<!-- tarav.breadcrumb 65783743765c -->
<!-- tarav.breadcrumb 78f78f9ea79a -->

Representation subtyping follows semantic class ancestry. Subclasses may
inherit or extend the interface, or deliberately use an independent one;
interface ancestry makes a separate independence flag unnecessary. The
framework exposes `is_record_subtype_of(A)` and the companion
`preserves_parent_record_interface()` query for direct parents.
<!-- tarav.breadcrumb 0eaf0abee399 -->
<!-- tarav.breadcrumb f34a258460e8 -->
<!-- tarav.breadcrumb 28532c7b75b3 -->
<!-- tarav.breadcrumb 9ea9114401ab -->

The final discussion retained the same inherited interface by default rather
than automatically manufacturing an empty interface subclass. Explicit
declarations express extensions. The design is integrated into
[the record-framework note](../record-framework.md#recordinterface-and-representation-inheritance).
<!-- tarav.breadcrumb 84eb8d4810f9 -->

## Record inheritance predicates

The RecordInterface relationship was normalized into function-style
predicates parallel to Python's `issubclass`: `issubrecord(B, A)` checks only
record-interface inheritance, while `isrecordsubclass(B, A)` requires both
behavioral and record-interface inheritance. This preserves separate
inspection of the two dimensions while naming the combined Tarav relationship
directly.
<!-- tarav.breadcrumb 1763fdf273a5 -->
<!-- tarav.breadcrumb fc7181ce074f -->

The existing `B.is_record_subtype_of(A)` API is to be replaced rather than
aliased or deprecated. The User established a current and near-future rule
that Tarav development does not retain legacy code.
