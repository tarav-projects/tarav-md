## Tarav was framed as a Python record framework

The design discussion clarified that User/Agent partitions concern the Model
workflow. Tarav itself is a broader ecosystem of lightweight JSON Records,
participating projects, and independent capture workflows. Its primary
programmatic interface is the Python library; the CLI supplies convenience
and efficiency. Records can live in central or externally hosted repositories,
initially on one computer. These ideas are captured in
[Tarav as a record framework](../record-framework.md).

## Compatibility belongs to participating workflows

The discussion introduced an explicit Workflow base to subtype and register,
while reaffirming registered classes as the authority for Record meaning.
External registration mechanics remain to be designed. The User rejected an
adapter-heavy solution: producers must make their Records compatible with
consumers, with at most minimal declarative path mappings rather than arbitrary
conversion code.

## Archive identity became a per-DOI contract

The discussion developed [Archive as a DOI registry](../archive-doi-registry.md):
each DOI commits to the same object while resolution can follow changing
locations. The archivist defines the contract per DOI. Archive-grade
references have a DOI root, optionally followed by a floating path or selector;
the Archive's promise covers the root. DOI issuance can be automatic or
requested by a subsystem, allowing commitment to grow progressively.

## Records made preservation a gradual commitment

The continued discussion defined Records as Tarav's JSON communication and
data units, able to contain data or point to it. The Record/Artifact distinction
is contextual: a Record can be an Artifact in another operation. Lightweight
descriptive Records preserve knowledge even when the described file or other
Artifact is lost. Hashes, locations, excerpts, and other hints can support
recovery searches. The design allows preservation cost to scale down under
constraints or expand into richer descriptions. These additions are integrated
into [the Record framework](../record-framework.md) and
[the Archive note](../archive-doi-registry.md).
<!-- tarav.breadcrumb e58747273b4f4bab88050a8e4125c02944c584f67f6719ff5c83396f27f08a8b -->

The User corrected a proposed universal observation/history interpretation:
those semantics belong above the common Record primitives. The Archive can
offer typed preservation capabilities without imposing a universal
object/edition model; Git-backed storage is one example of obtaining edition
capabilities. Subsystems remain free to choose and combine the Archive's
preservation capabilities.

## Navigation became a workflow over registered providers

The discussion extended the Record graph with general navigation: Agents
should be able to start from a root listing, enter a project or collection,
list its contents, and continue exploring. Collections register subroots,
such as a Tarav project or an archive, rather than registering every Record.
Navigation itself is another workflow. This is integrated into
[the Record framework](../record-framework.md).

Providers must expose the routes needed to reach their Records; errors
surface as POIs.

## References gained locator, check, and hints

The discussion introduced references as typed primitives supplied by workflows
and sharing general Tarav principles. A locator finds the resource; checking

`locator`, `check`, and `hints`. This is captured in

## Tarav became an external harness over selected workflows

The discussion added an external-harness narrative to Tarav. Agents remain
controlled by the user and their native harness. Tarav is a formalization layer
that becomes active when an agent executes a Tarav workflow, such as capture.
The workflow graph provides typed context and possible actions before
generation, then lints the resulting action and state afterward.

## Workflows preserve multiple solutions and their semantics

The discussion returned to why Tarav is a framework: one capture design does
not serve the full spectrum of collaboration. Quick prose, Model maintenance,
sidequest notes, governing Constitutions, and brainstorm vaults have different
uses. Workflows can overlap in functionality rather than mapping one-to-one to
use cases. Navigation and contextualization integrate the resulting data and
surface its semantics, with capture and contextualization workflows aligned

## Harnessing became a short feedback loop through library operations

The discussion framed harnessing as pregeneration context and postgeneration
audit, with each step's findings feeding the next step's context. The User
emphasized cooperation by a good-faith agent and the compiler analogy:
short check/revise loops solve detectable classes of defects without needing
to prove all semantic correctness. Convergence means no deviations detected
by the available checks.

## Skillware framed generation as an assessable activity

The User introduced Skillware (`skw`) as a generation programming language:
named, reusable, composable generation functions with arguments, arbitrary
text bodies, and context, interpreted by agents. Its typical output is a file
or fragment, and any file can be harnessed. The discussion is integrated in
[Skillware](../skillware.md).
<!-- tarav.breadcrumb 5f0a3591b213166abfa7f91e3293661cd43728ec9cdbba5827013a9d0cdd5443 -->
<!-- tarav.breadcrumb aba127cbf937bd6a363a2d3b3ef4e4c7e77236f196e14e0c0485f8112a152e59 -->
<!-- tarav.breadcrumb 8fafb03e05d10bcdfe2496a8fd1124d55c9d312b2e81b7d82b9bfc51da46c30c -->

Two obligations became explicit: generation dependencies concern what the
agent must have in context; output assertions concern what the surface must
satisfy. Context can come through Tarav contextualization workflows or another
prompt. Declared requirements and the context actually received remain
distinct, with the producing chat providing evidence for later audits.
<!-- tarav.breadcrumb 49560dbb9689721f4502613ece62d827c69ac7373d677d16f05a753584f40281 -->
<!-- tarav.breadcrumb 14f37a80a401e993acee389cc343c3b8d7399f9b13cc1fe951915f5af04b975c -->

Tracking outputs and their dependencies enables change-triggered review POIs.
Invalidation reports a reason, such as changed context requirements; it does
not adjudicate the output as wrong. These capabilities can grow progressively.

The User chose an independent Skillware MVP with typed prompt arguments,
generation-block dependencies, and basic linting. A separate reference-based
dependency-annotation workflow can coexist. Initial duplication is acceptable;
shared mechanics can be extracted later rather than imposed up front.
