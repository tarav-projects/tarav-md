## Qualifying Python APIs

The user proposed namespaced paths such as `SomeType.loadings.from_path(...)`
and `obj.records.to_record()` as another way to reflect Tarav's organization
in code. The direction is optional and evolutionary: use qualification when a
widely inherited base-class API grows crowded or loses context, while leaving
workflows free to expose clear methods directly. The path is a semantic cue,
not a rule that mechanics must depend on. See
[Namespaces as semantic qualification](../diagram-workflows.md#namespaces-as-semantic-qualification).

## Dependency layers as modeling room

Following the namespacing discussion, the user proposed splitting namespaces
such as Kernel across dependency layers. Dependencies run downward between
layers, with no additional directional restriction inside a layer. Begin with
this as a design principle and defer enforcement tooling. The discussion
distinguished avoidable packaging cycles from genuinely circular definitions:
layering addresses the former without claiming to solve the latter. This is
design capture, not a package reorganization. See
[Dependency layers across namespaces](../diagram-workflows.md#dependency-layers-across-namespaces).
