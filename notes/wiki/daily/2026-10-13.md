## One product drift action, read closely

The User pasted the status row of an open product drift action and asked to
discuss it. The row said only `product-drift`. Its situation held the hash
of every file of the package.
<!-- tarav.breadcrumb a18571701062 -->

The User defined the situation as the declared state, the one a blessing
targets and the POI represents, and accepted three fields for this Type:
the product, the hash of the file, the hash of the text its source
produces. A heuristic followed: a situation is what the check actually
uses. Built as request 902 for this Type only; the drift itself was not
repaired. See
[POI visibility, navigation, and blessings](../poi-system.md), section
"Product drift declares its own situation".

## POIs become data in one way

Asked what an action stores of its POI, the agent named two methods,
`as_dict()` and `describe()`. The User had approved neither and ordered
them destroyed, for any Tarav object that fakes serialization: the Record
system is the serialization path.
<!-- tarav.breadcrumb 389eb0c4bb11 -->
<!-- tarav.breadcrumb fca6c446b460 -->
<!-- tarav.breadcrumb 6f89eac7991d -->

Every POI Type now defines its record and loads back from it. The Diagram
POI's `to_dict()` was the stored shape of 13,347 rows in the Diagram Drafts;
the User asked for the migration, since legacy data and code are not
tolerated. The older Draft migration command was deleted and its backup
moved to the Attic (Deposit `60494dc6-673c-4310-9d10-c8e766f6deb1`).
<!-- tarav.breadcrumb dacc2812a007 -->
<!-- tarav.breadcrumb 1b5ef872ffb3 -->

On the details of a POI the User set the scope: a bundle of data that helps
agents, best effort, outside the identity, and nothing mechanical relies on
it. The agent's test for the boundary was accepted as a heuristic: if
removing the details changes what any code does, that value is not a
detail.
