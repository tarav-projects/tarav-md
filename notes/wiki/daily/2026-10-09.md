## From a POI to the Operator Context

A POI pasted from Tarav Center started a discussion on what a POI should
carry. The User framed it as the producer's intention made clear for a reader
whose goal the producer cannot know, asked for a general `.throw()`, and moved
"what to do" out of the POI and into the reader's skill and context.

From there the User proposed that agents state their intention as a typed
object, a Directive, so the code knows who is calling and can condition
context, checks and gated actions on it.
<!-- tarav.breadcrumb eb2229878b8d11270af74adbbaaf7d4eef9b9970e1aec8a99d5c974ebbd3c19b -->

The unit of controlled work was named a Harnessed Action: a declared start, a
conditioned middle and a reserved final stop for validations, with the dial
set mostly by checks and consequences felt later, not by hard stops. The User
sees Programs and Actions as the same nature.

folder with a main record in the Project's `.tarav/`, linked to the session
and maintained by the agent, where workflows keep their own spaces. It
formalizes the first node of any pipeline.

## Tracked POIs become actions

Walking through the Actions example, the User asked what a blessing means and
arrived at a simpler model: a POI is only the event; what persists and gets
worked on is an action it spins, with several close paths, one of them
dismissal. A tracked POI becomes an actionable POI, and an Actions loop closes
runs whose close path is met. See [POI system](../poi-system.md). Request 892
in `tarav-py` designs the rebuild; it was not executed.
