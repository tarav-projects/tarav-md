## Reading graph type family

SKW Code now owns an abstract `ReadingGraph` contract. The existing Skill
package analyzer is `SkillReadingGraph`, while Project owns an abstract
`ProjectReadingGraph` specialization that binds a Project without inventing a
default onboarding route. This follows the selected bootstrap order: establish
the shared Type and the two semantic branches first, then extract additional
mechanics only when both applications demonstrate them.

## Live Help and the CLI model

Reviewing what that skill change cost led the User to a broader design: Agents
should learn Tarav from live material, meaning source code and recent real
uses, with documentation last. The CLI becomes Tarav objects, every `tarav`
call is recorded in the CLI workflow's central storage partition, and a
reactive Live Help section becomes a standard part of every `--help`. The code
stays dumb and hands over leads. See [Live Help](../live-help.md); the design
request is note 851 in `tarav-py`.

## Pairwise tribunal scoring

Request 848 added a reusable tribunal path after the closed-case foundation.
A typed tribunal supplies the comparison question and admission boundary;
the common ranker presents two closed cases and records A, B, tie, or abstain.
Results yield relative support within that tribunal, with comparison counts
and coverage shown separately. A single case stays unscored, and weak rank
does not mean falsehood. The product commit is `tarav-py` `bd5be10`;
61 focused scoring, architecture, and POI tests passed. See
[Assertions and scoring](../assertions-scoring.md).

## Lessons from g70203: decisions, tracked POIs, attention

While redesigning g70203 on Tarav, the User asked that what was learned be
documented in Tarav itself, and an implementation request created here.
<!-- tarav.breadcrumb 2a8d1465ef28 -->

A Tarav system is a superposition of workflows, each aimed at one problem,
sharing a significant amount of primitives; md-library's lint and co-reading
passes are the reference example.
<!-- tarav.breadcrumb 6aaa06c3de94 -->

Blessings are one kind of Decision: the interventions made in a system,
recorded and continuously asserted. Orders and blessings are asymmetric, and
user decisions are not scores. See [Decisions](../decisions.md).
<!-- tarav.breadcrumb ea7c35858363 -->
<!-- tarav.breadcrumb 8f6af7801d0b -->

Recorded POIs are now called tracked POIs; they sit on a board that any
workflow can filter, and "Attention" names the ranking workflows. See
[POI system](../poi-system.md#tracked-pois-the-board-and-attention).
<!-- tarav.breadcrumb 21635089cb5f -->
<!-- tarav.breadcrumb 00f04bd5e14e -->

Usage traces then became typed: a base trace type that others subtype, with
each type's owner rendering its traces and help filtering by type, so Live
Help needs no knowledge of the CLI. Designed as note 855 in `tarav-py`.
