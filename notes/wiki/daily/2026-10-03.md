## Reading graph type family

SKW Code now owns an abstract `ReadingGraph` contract. The existing Skill
package analyzer is `SkillReadingGraph`, while Project owns an abstract
`ProjectReadingGraph` specialization that binds a Project without inventing a
default onboarding route. This follows the selected bootstrap order: establish
the shared Type and the two semantic branches first, then extract additional
mechanics only when both applications demonstrate them.

## User Brief workflow

The User asked for a workflow in which an Agent explains a POI, an Agent
statement, or the state of part of the system from first principles. Agents
implemented most of the system, so the User's knowledge is partial and Agent
reports often lack the context needed to read them. The briefing must link the
subject to conversations the User already had, for example by following
Breadcrumbs, and stay economical. See [User Brief](../user-brief.md).

`--brief` as its shortcut, authored through SKW.

## One Python runner

The User selected `tarav run [--project [PATH]] -- <python arguments>` as the
single script entry point and removed the duplicate `project harness run` and
`python run` CLI leaves. The library remains the main interface, with no
injected Project object or library restructuring. Bare `--project` discovers
the nearest Project upward and errors if absent; omitting the flag uses the
global Tarav interpreter even inside a Project. The installed command, md-library
example, and 46 focused and architecture tests passed. See [Tarav.Harness](../tarav-harness.md)
and `tarav-py/notes/live/850-unified-run-cli-impl-req.md`.

## Live Help and the CLI model

Reviewing what that skill change cost led the User to a broader design: Agents
should learn Tarav from live material, meaning source code and recent real
uses, with documentation last. The CLI becomes Tarav objects, every `tarav`
call is recorded in the CLI workflow's central storage partition, and a
reactive Live Help section becomes a standard part of every `--help`. The code
stays dumb and hands over leads. See [Live Help](../live-help.md); the design
request is note 851 in `tarav-py`.

## Assertable cases

The User chose an object-to-Assertions-to-cases chain for scoring. Request 846
implemented the first shared contract: an Assertable exposes labeled Assertions,
and an Assertion can produce a typed, closed assessment case. The scorer receives
the supplied claim, question, and material rather than researching missing
evidence. Unsupported case Types and incomplete material remain different
outcomes. The Line grounding Assertion demonstrates two case payloads; its
existing identity and ranking adapter remain unchanged. The product commit is
`tarav-py` `230b98a`; 47 focused scoring and architecture tests passed. See
[Assertions and scoring](../assertions-scoring.md).
