## Context graph as a way to discover Tarav

Captured the discussion of October 16 about how Python code and the Context
graph work together. The User corrected an emphasis on missing Archive links:
Chatlas transcripts are the present reference focus, and other subsystems can
join the graph through their Tarav objects and Context contributions. The
graph can describe Tarav's own code as well as external material, letting an
agent investigate an unfamiliar object and follow paths back to code and
resources.
<!-- tarav.breadcrumb 79b7c0c95f41 -->
<!-- tarav.breadcrumb 795b85f1fbf4 -->

The User used documentation to distinguish semantic discovery from direct
execution: the graph may identify and explain a documentation relationship
and lead to an object pointing at the resource, while code can directly open
or display it. A proposed recorder could relate scripts or operations to the
Types and objects they use, supporting repeated searches for examples. The
User ended by setting aside a rigid code-versus-graph placement rule: write
the code needed for the task and use the graph to communicate and discover
its semantics. See [Discovering Tarav through its graph](../rdf-diagram-experiment.md#discovering-tarav-through-its-graph).

Reviewed a Codex session's request 918 for 12-character Breadcrumb labels. The
User confirmed the design, declined a generation rule that would keep
12-character prefixes unique by construction, and ran it as `--impl --dev`
with one addition: migrate every existing marker. Tarav-py now resolves
prefixes, writes 12-character labels on surfaces and in commit messages, and
reports collisions with the colliding IDs. See [Short labels](../breadcrumbs.md#short-labels--2026-10-18).

checkpoint and a migration commit. Audits before and after matched everywhere
except where another session edited the Constitution during the run. The
User then asked to audit why audits were slow; the cause is the
chatlas-context audit rebuilding Chatlas Normal Models instead of using their

## Chatlas cache freshness, towards a Tarav Center chat view

<!-- tarav.sessions
3537df0a = claude-code:2bff854f-66a0-4e8c-8f96-9078af34c479 @3537df0a6015d884a94e9594478f971cb92e38df63776b87b5eea38741740d8a
-->

The User asked for a Chatlas workflow in the Tarav Center extension: search
chats and view one, with the extension as thin a wrapper around Tarav as
possible. Inspection showed that cross-chat search had nothing to stand on:
only 71 of about 10,000 sessions had a cached Normal Model. The User chose to
improve Chatlas first, so that at least the Normal Model is cached and
Chatlas is usable from outside.
<!-- tarav.breadcrumb 0af8489e9412 -->
<!-- tarav.breadcrumb 72ff61c7f43a -->

The depot stopped tracking the derived `normal-model/` cache in Git, and the
stale `session-models/` and `chatlas2/` caches were removed. The cache was then
redesigned: freshness depends only on a `raw_version` of the raw data, each
part is judged separately, and the library returns what is stored with a stale
flag while public surfaces stay safe. See
[Cache freshness from the raw data](../chatlas-normal-model.md#cache-freshness-from-the-raw-data--919).
<!-- tarav.breadcrumb 0a91d48b19e4 -->
<!-- tarav.breadcrumb f48e03a8d6b6 -->

A cross-session search index and JSON surfaces remain under discussion; the
User asked to look first at what Chatlas already offers, so that the command
surface does not grow redundant systems.
