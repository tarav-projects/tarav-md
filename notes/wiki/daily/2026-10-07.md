## TaravRecords implementation design

The discussion settled on `TaravRecords` as a workflow for reusable Record storage primitives and basic discovery and navigation across workflow-owned storage. The desired graph is built from hooks into those storage solutions, without a central entry for every Record. Archive retains its separate Artifact and long-term preservation meaning; a Registry is a way to store Records and may be used by Archive. Tarav can provide standard Registry locations while other workflows keep custom storage. The candidate implementation boundary and its open migration question are recorded in [Impl.Req 864](../../../../tarav-py/notes/live/864-tarav-records-workflow-impl-req.md) and [TaravRecords](../tarav-records.md).

## TaravRecords first implementation

The User selected an incremental boundary: organize the Records workflow and share primitives that can be extracted or adopted easily, while other workflows retain their own storage and later alignment remains open. The implementation adds a contributed-source explorer, an optional standard Registry partitioned by Workflow, an on-demand Entity view, and common typed write and Git operations. Archive and Scoring provide unlike sources without a central list of individual Records. The existing Record Archive layout remains in place. See [TaravRecords](../tarav-records.md) and [Impl.Req 864](../../../../tarav-py/notes/live/864-tarav-records-workflow-impl-req.md).

## Object namespace implementation

The User chose an object-level namespace pattern: a class selects a namespace class (`P`), while an instance exposes a bound lowercase path (`p`). Independent bases may contribute to the same namespace; the combined class explicitly selects a namespace subclass of both. The User asked for an automatic check against silently losing one contribution. [Impl.Req 865](../../../../tarav-py/notes/live/865-object-namespaces-and-composition-check-impl-req.md) records the bounded implementation.

## Project capability paths

The User selected explicit Project paths: `project.docs.wiki.daily(date)`, `project.models.ls()`, and `project.checks.run()`. Documentation sits under `docs`, Models remains its own capability, and Checks is a shared provider namespace whose suite can be obtained without running it. This places shared or abstract operations under paths that explain their provenance.

## Namespace style heuristic

The User refined namespaces into a common design style rather than a rule for every abstract method. They are especially useful for capabilities shared by heterogeneous subtypes, such as `.checks` supplied by `CheckProvider`, and for organizing a large object, such as `project.models`. A namespace may express an extension or merely clarify an object's own API. [Record framework](../record-framework.md) holds the topical formulation.

## Record namespace class loading

The next implementation step completed a class-side Record path: `SomeType.records.from_record(record)` pairs with `obj.records.to_record()`. The kernel registry now loads through that path, with direct calls retained during broader caller migration. The [Record framework](../record-framework.md) captures the API arrangement and [Impl.Req 867](../../../../tarav-py/notes/live/867-record-namespace-class-loading-impl-req.md) records the code and verification.
