## The status command was too slow; suites return as detectors

`tarav project status` ran the whole pytest suite of `tarav-py` on every
call. The User wants it to be the constant mechanical feedback for agents,
so it cannot be slow, and agents should be able to run a subset.
<!-- tarav.breadcrumb 8ab69e79f90a -->
<!-- tarav.breadcrumb 88cf5f336014 -->

Running a subset needed a new closing rule, and the discussion brought the
suite back in a different form from the one removed the day before. A suite
is a class with an identity. It does not contain checks: it contains the
code that runs them, because checks depend on situations and cannot be
listed beforehand. It holds the results of its one run, and it can run whole
or filtered. The signal is gone when the detector no longer detects it.
<!-- tarav.breadcrumb 543f44bb4b6d -->
<!-- tarav.breadcrumb 8ad9dbbacd5f -->
<!-- tarav.breadcrumb e93227462d8b -->

Built as request 899: the pytest tests are a suite with one suite per test
file, left out of the routine run, and `--all` runs everything. The old
action records were deleted and reopened. See
[POI visibility, navigation, and blessings](../poi-system.md), section
"Suites are detectors that hold their run".

## The POI is a flag; actions are the unit of work

Starting from the hint the status printed, the discussion went to
fundamentals. A POI is a flag between detecting and working: momentary,
owning nothing. A consumer decides what happens to it; the Project status
escalates what its checks raise to actions, and printing is only how a
person looks at checks. Blessing, filtering and anything else that
integrates several workflows is modeled on the Project. The store of
reported POIs and the blessing machinery on the POI side were removed.
Built as request 900; see
[POI visibility, navigation, and blessings](../poi-system.md), section "The
POI is a flag; the Project integrates".

## The POI model reduced to its fundamentals

Fixing the drift made many actions end and restart, which led to the POI
model itself. The agent twice described more than the model holds. The User
separated a line's choices from the principles: a `POI` has a Type and a
message; a `SituationPOI` adds a situation, any object describing it, and
Type plus situation is the identity; everything else is a field a
specialization adds. `subject` and `evidence` were removed from the base.
Built as request 901; see
[POI visibility, navigation, and blessings](../poi-system.md), section "A
SituationPOI has only its situation".
