## Python execution and Diagram ontology

The class-reification design acquired a clearer boundary. Python classes remain
Tarav's executable layer and retain all domain functionality. The Tarav Diagram
is the ontology layer: it gives those classes common identity, meaning, and
relationships without replacing or executing them. A `TaravClass` is therefore
the ordinary Diagram Entity representing a Python class.
<!-- tarav.breadcrumb 88e90f3600d1 -->

The general graph is the Tarav Diagram, with a minimal built-in spine beginning
at `TARAV -> Workflow -> Type` and room for each Workflow to add its own
subjects and vocabulary. Diagram-facing access should cross an object boundary:
`entity(SomeClass)` returns its `TaravClass` instead of exposing ontology fields
directly on the Python class.
<!-- tarav.breadcrumb 83560e85c8c1 -->

Each participating class supplies a `class_entity()` hook that directly
constructs its `TaravClass`. The discussion rejected an additional
`TaravClassDeclaration` object and a nested factory because the hook already
owns arbitrary construction logic. The resulting Entity represents the class;
runtime behavior remains on the represented Python class.
<!-- tarav.breadcrumb 1668f71d1b95 -->
<!-- tarav.breadcrumb c5e7a64be8ed -->
<!-- tarav.breadcrumb a8123fb4f085 -->

The current Python bootstrap still stores Type identity on class attributes,
so moving those ontology fields behind `class_entity()` remains a subsequent
implementation change rather than completed behavior.
<!-- tarav.breadcrumb 0bcd3227452d -->

## Records as object projections

The `TaravObject` design was refined around a stronger separation: the Python
class and object own semantics, behavior, and runtime state; a Record is a
class-selected projection of that object, not its data model. Every
`TaravObject` still declares a `RecordInterface` so Tarav can validate the
chosen representation, but that interface does not prescribe the object's
internal state, construction strategy, persistence, or domain schema.
<!-- tarav.breadcrumb 37530e44dc9c -->
<!-- tarav.breadcrumb b3660a0be182 -->

Tarav may retain an optional private `_record` populated by its loading
mechanics. That value records the loaded representation; it is not the
object's source of truth, and a runtime-created object need not populate it.
The object remains free to hold and organize its authoritative state however
its class requires.
<!-- tarav.breadcrumb 6281a99d9557 -->

The public `to_record()` operation should own the stable workflow of selecting,
validating, detaching, and returning a representation. It calls the protected
`_to_record()` hook, which each class may override to project `_record`, runtime
state, external state, or any combination. This lets Tarav control integration
mechanics while preserving representation freedom.
<!-- tarav.breadcrumb cc5189d7dc47 -->

## Record validation boundaries and object interfaces

The Record contract was narrowed further. Its coherent common mechanics are
the two validated boundaries: Record to object through `from_record()` and
`_from_record()`, and object to detached Record through `_to_record()` and
`to_record()`. When a representation extends its parent's representation,
extending `super()._to_record()` is the preferred practice; explicit fresh
construction remains available for a deliberately independent representation.
<!-- tarav.breadcrumb 24beb99fcbf8 -->

The proposed public `record_data` view was rejected because it would define a
data-access convention for all Tarav objects and blur the Record's role as a
projection. Tarav validates at explicit validation, loading, and writing
boundaries. Classes own their runtime state, semantic fields, and any syncing
with the optional `_record` supplied by loading.
<!-- tarav.breadcrumb cc9efbca63ed -->

`TaravEntity` may still promise an `id: Ship` field because identity is part of
the Entity interface. Its implementation is responsible for wiring that field
to and from its Record representation; this does not establish a generic data
interface on `TaravObject`.
<!-- tarav.breadcrumb 5dda9c5972e8 -->

## Exact loading and post-load Python behavior

The loading boundary was clarified. Tarav owns the validated
`Type.from_record()` path, while a Type owns its `_from_record()` construction
hook and may expose any other constructors it needs. The dynamic
`load_object(path)` path locates a Record, resolves its registered concrete
Type, and constructs through that Type. Its optional keyword-only
`expected_type` asserts the exact resolved class before construction; it does
not choose a class or ask Tarav to upcast a child Record to a parent.

The loaded object's `_record` is expected to belong to its concrete class.
After Tarav delivers that object, the Record Type mechanism has finished its
job; inheritance and cooperation between classes follow ordinary Python
rules, with responsibility for those relationships resting with the classes.

## Context as a retained and runtime directory

The Context design expanded beyond Type and object hooks. An Entity's durable
context can live under `~/Documents/tarav/contexts/`, in its own directory,
where Workflows can add Records and nested directories. Each retained
directory should have a `DirectoryRecord` and a cheap local registry so `ls()`
can discover entries without loading their contents.
<!-- tarav.breadcrumb 1bbd3e7589b2 -->
<!-- tarav.breadcrumb b51a81becbed -->

`Context` is a read-only, stateful navigation cursor: `cd()` changes its
position, while runtime and retained entries appear at the same point in one
virtual tree. A Context maps names to `TaravObject` or nested `Context`
values. The parent Context owns each name; an opened object need not know where
it was placed. `open(name)` returns the object or nested Context, and `cd(name)`
enters a nested Context.
