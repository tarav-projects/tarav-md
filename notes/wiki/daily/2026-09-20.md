## Breadcrumbs as surface attachment points

The discussion generalized the inline Chatlas context comments into
`Tarav.Breadcrumbs`. A Breadcrumb is an opaque stable anchor embedded in a
Product.Surface, not the annotation itself. Workflows attach independent typed
records to that position, allowing context, implementation provenance, and
other semantics to share the same surface point.
<!-- tarav.breadcrumb fb82ff041e443431bc6672f1d2a42295c31e127077c9d045bb9c1d37e512be65 -->
<!-- tarav.breadcrumb 6b552c7e58a10f647be7182e2a620775b01f72309dc8800ee12ce6ff025f57db -->
<!-- tarav.breadcrumb 852d0bfd3a7423996025abc7bc9034bf302259e98b15dc7f625fd2e4bc4a4261 -->

Agents may attach records directly or use a specialized surface workflow. A
workflow can accept cheap temporary annotations, parse and resolve them at the
end of capture, create Breadcrumb and attachment records, then replace the
temporary syntax with the canonical opaque label.
<!-- tarav.breadcrumb f6be2fa7572d874188318b90216db97203b730f7c507052ca67122ed4d859a27 -->
<!-- tarav.breadcrumb 6e53eb964ef92d81c764a30493e7d26244e953b2f7e139a13ff7fbd7618eb8cf -->
<!-- tarav.breadcrumb b74a1f9d8ced4499b39054b6de6d6adaa5dae2581273eca6aa7415e642a4acb7 -->

The selected storage direction gives each Breadcrumb ID its own directory.
Stable identity remains in `main.json`; changing position observations append
to JSONL; workflow-owned attachment records remain independent of the
Breadcrumb core.
<!-- tarav.breadcrumb d00517eda4ea8cc97bc7fa91eaa1c6c4c3866982f45bf69b65a67bb58d20f20e -->
<!-- tarav.breadcrumb 6c64d85702377007806bdb71b6f0f4b3d6997591fd433b4befb589dabe877602 -->

Position observations use a normal `FilePositionReference`: file and line are
mechanical locator data, while neighboring line fragments are hints ignored by
resolution. The file field may be either a simple path or a typed
`FileReference`, demonstrating the rule that only top-level Tarav Records must
be typed and embedded typing remains application-dependent.

## Chatlas Normal Model ownership

The discussion promoted the Chatlas Normal Model aggregate itself to a
directory-backed Tarav object. Its normalization module owns the semantic
class, on-demand materialization, and canonical folder representation; being
derived and rebuildable does not make the Model a cache-owned object.
<!-- tarav.breadcrumb b681752ebce0346965560d104c57d43b10ad86d62b3915739c2023e8307f9b1d -->
<!-- tarav.breadcrumb e978054dbd791bb9ad7f99abbf32453993dfd869cf9f5a8ea7ec2975935d5a96 -->

Chatlas cache mechanics remain outside the Normal Model module. They may add
an ordinary `cache.json` beside the Model-owned files, but its absence or
invalidity affects cache reuse rather than Normal Model validity. This keeps
the Normal Model at the directory root instead of wrapping it in a cache
entry or treating the cache as a semantic subtype.
<!-- tarav.breadcrumb 0432355439807bc80736a0b0d9bbfd484075e2b7c6b9383ad5ce2e08d7e4f326 -->

The design is integrated in the [Chatlas Normal Model topical note](../chatlas-normal-model.md).
