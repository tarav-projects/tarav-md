## SKW objects and ordinary record loading

The discussion proposed representing skills as Python objects and using
`.skw/main.json` as a common typed entry point. The direction is to unify SKW
loading with regular Tarav directory records, with a skill specialization such
as `SkwSkill` inheriting from a general `SkwDepot`. These are design decisions
for subsequent implementation, captured in [Skillware](../skillware.md#typed-skw-depots-and-skill-objects).

The User clarified that type dispatch should fit ordinary Python class
relationships. A mismatched declaration can fail under the selected class's
interpretation; each class owns its due diligence instead of requiring a
universal correctness gate. This is also recorded in the
[record framework](../record-framework.md#type-dispatch-and-class-responsibility).

## Context navigation belongs to the agent

The large Skillware context-command output prompted a design correction:
agents should choose what to expand and avoid reloading context they already
have. The User proposed filesystem-like ls, head, tail, and full-read
primitives, plus resolved absolute paths usable through the agent's own tools.
This is captured in [Skillware](../skillware.md).
<!-- tarav.breadcrumb 06d91a6441b0 -->
<!-- tarav.breadcrumb cf572847ac49 -->
<!-- tarav.breadcrumb 5146da10a598 -->

The User generalized this into a Tarav design principle: keep mechanics simple
and supply navigation tools and hints rather than flooding the agent, at least
where context efficiency matters. The agent is the navigator. This is also
captured in [Tarav.Harness](../tarav-harness.md).

## Skill packages, model publication, and dependency roles

The discussion revisited the Attic's old Index and Kernel-block ideas for
Markdown documentation used by skills. The resulting direction is
`Diagram.Model → Md.Model → Other.Surfaces`: Md.Model is a compiled deployment
of required model content, not an independent modeling or generation surface.
Changes remain in Diagram.Model. Markdown also offers convenient findability.

The User separated developer context dependencies from consumer dependencies.
Maintainers may use Diagram directly; consumer context should default to
bundled skill content or references to other skills, navigated through routers
and indexes. Explicit code-based tracking supports these dependency networks.

## Declared loading paths and consumer-context analysis

The published model example raised the question of how a consumer knows what
`[PR]` means. The discussion distinguished build-dependency freshness from
consumer-context sufficiency and located the latter in `skw.skills` as static
analysis, not runtime tracking. Every consumer block should be on a declared
loading path; checks should expose unreachable blocks, missing context, and
path-dependent coverage.

The User clarified that the objects are SKW blocks. Mechanics track blocks,
not the meanings an agent learns from them. Blocks declare context requirements
with referenced, inlined, or unspecified delivery, plus their own outward links
and inclusions. Parent attachments form loading paths, defaulting to file
predecessors and sharing the skill entry root (`SKILL.md` by default).

dependency and loading mechanics; parsing generated output is permitted for
primitive-specific conformance checks, not graph discovery. The design and its
corrections are captured in [Skillware](../skillware.md).

## Navigable POIs and recorded blessings

The User requested POI primitives that let agents discover what a check means
and where its documentation lives, and record agent blessing actions so they
can be scored. Blessed findings should remain visible with their blessing
status. Some POIs are not blessable and instead require fixing the analyzed
surface.
<!-- tarav.breadcrumb 210f57d90030 -->
<!-- tarav.breadcrumb 28ec4648c035 -->

The discussion separated detection from presentation: retain all findings,
while exposing compact groups/counts and bounded navigation to protect agent
context. POIs behave like automatic issues; the user or agent chooses which
to address in the current workflow. The initial navigation can simply expose
the POI class path. These principles are integrated in
[POI visibility, navigation, and blessings](../poi-system.md).
